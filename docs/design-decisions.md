# Принятие решений

## 1. Multi-module Architecture

### Контекст и задача
По мере развития проекта количество тестов, поддерживаемых платформ и вспомогательных компонентов увеличивается. Размещение всего кода в одном модуле усложняет управление зависимостями, конфигурацией и структурой проекта.

### Принятое решение
Проект организован с использованием многомодульной архитектуры Gradle. Каждая платформа автоматизации вынесена в отдельный модуль со своими зависимостями и тестовой инфраструктурой.

### Обоснование и преимущества
Такой подход позволяет:
- Разделить ответственность между платформами, изолировать зависимости разных инструментов автоматизации.
- Упростить поддержку и развитие отдельных направлений тестирования.
- Повторно использовать общие компоненты там, где это необходимо.
- Независимо запускать тесты отдельных модулей.

## 2. API Testing Architecture

### Контекст и задача
API-тесты взаимодействуют с серверной частью приложения и включают несколько типов операций: отправку HTTP-запросов, обработку ответов, проверку результатов и описание тестовых сценариев.

Размещение всей логики непосредственно в тестах приводит к дублированию кода и усложняет его поддержку.

### Принятое решение
Для API-автоматизации выбрана слоистая архитектура с разделением на пять уровней:

1. Tests: Описание тестовых сценариев
2. Assertions: Проверка ответов и бизнес-условий
3. Services: Обработка ответов
4. Clients: HTTP-взаимодействие
5. Models: Модели запросов и ответов

### Обоснование и преимущества
Разделение позволяет:
- Изолировать HTTP-взаимодействие от тестовой логики.
- Повторно использовать API-операции в разных сценариях.
- Централизовать проверки и обработку ответов.
- Упростить изменение реализации отдельных компонентов.
- Повысить читаемость и поддерживаемость тестов.

Например, при изменении способа отправки HTTP-запросов достаточно изменить соответствующий Client, не затрагивая тестовые сценарии и Assertions.

## 3. UI Testing Architecture

### Контекст и задача
Web и Android UI-тесты взаимодействуют с элементами пользовательского интерфейса. При непосредственном использовании локаторов и действий с элементами внутри тестовых методов возникает зависимость тестовой логики от структуры страниц.

Изменения интерфейса могут приводить к необходимости редактировать большое количество тестов.

### Принятое решение
Для Web и Android UI-автоматизации используется подход, основанный на Page Object Model (POM).

Страницы и отдельные функциональные области интерфейса представлены соответствующими объектами, инкапсулирующими локаторы и методы взаимодействия с элементами.

Тестовые классы содержат сценарии и проверки, а Page Objects отвечают за взаимодействие с интерфейсом.

### Обоснование и преимущества
- Разделение тестовой логики и логики взаимодействия с UI.
- Повторное использование методов и локаторов.
- Централизованное управление элементами страниц.
- Упрощение поддержки при изменении интерфейса.
- Повышение читаемости тестовых сценариев.

Например, при изменении локатора кнопки авторизации достаточно обновить соответствующий Page Object, не изменяя все тесты, которые используют эту кнопку.

## 4. Test and Framework Code Separation

### Контекст и задача
Автоматизация включает как непосредственно тестовые сценарии, так и вспомогательные компоненты: базовые классы, конфигурацию, клиенты, Page Objects и другие элементы инфраструктуры.

Их смешивание затрудняет понимание структуры проекта и повторное использование компонентов.

### Принятое решение
Код разделён между директориями main и test в соответствии с соглашениями Gradle:
- src/main — инфраструктурный код автоматизации: базовые классы, конфигурация, клиенты, Page Objects и другие общие компоненты.
- src/test — тестовые сценарии и компоненты, используемые исключительно в тестах.

### Обоснование и преимущества
- Разделение инфраструктурного и тестового кода.
- Более понятная организация исходников.
- Возможность повторного использования компонентов.
- Соответствие стандартной структуре Gradle-проектов.
- Упрощение управления зависимостями и сборкой.

## 5. Configuration Management

### Контекст и задача
Для запуска тестов на разных окружениях и устройствах требуется изменять параметры подключения, настройки браузеров, эмуляторов и другие параметры выполнения.

Хранение таких значений непосредственно в коде приводит к необходимости изменять исходники при смене конфигурации.

### Принятое решение
Для управления настройками используются properties-файлы.

Конфигурация разделена на два уровня:
- application.properties — общие настройки проекта, используемые по умолчанию.
- local.properties — локальные параметры запуска и настройки конкретного рабочего окружения, включая секреты. 

local.properties добавлен в .gitignore, чтобы в общий репозиторий не попали локальные настройки и секреты.

### Обоснование и преимущества
- Отделение конфигурации от исходного кода.
- Возможность запускать тесты с разными параметрами без изменения реализации.
- Упрощение локальной настройки проекта.
- Снижение риска попадания персональных настроек и секретов в репозиторий.
- Централизованное управление параметрами запуска.

Например, адрес тестового окружения или тип запуска Android-устройства можно изменить через конфигурацию, не затрагивая тестовые классы.
